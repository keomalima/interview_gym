# Interview Gym — v1

## Product
A personal workspace for realistic technical interview practice. The longer-term curriculum covers JavaScript/TypeScript algorithms, business logic and data processing, debugging, React, SQL, and architecture. Start with business problems rather than puzzle-only exercises.

Milestone 1 delivers a complete local practice session. The practical category contains three original TypeScript business-logic challenges: fictional token pricing, usage billing, and request-log aggregation. Each has requirements, starter code, examples, progressive hints, executable tests, and a verified reference solution. The user expanded the v1 scope on 2026-10-07 to include a small Algorithms category with two JavaScript exercises (target pairs and matching brackets). Inputs and expected outputs are visible before running each test. The screen adapts `mock.png` with a larger editor, collapsible navigation/brief, console and tests underneath, and remembered dark/light mode.

## Architecture decision and early validation
- React + TypeScript with Vite for the interface; CodeMirror for editing.
- Sandpack was evaluated against its [official architecture](https://sandpack.codesandbox.io/docs/architecture/overview) and [bundler documentation](https://sandpack.codesandbox.io/docs/guides/hosting-the-bundler). Its framework preview/remote bundler adds an unnecessary execution dependency for standalone functions. Milestone 1 uses an offline browser runner instead. Sandpack remains a candidate for the later React format.
- TypeScript is compiled in a disposable Web Worker. Learner JavaScript runs in a second disposable Worker inside a sandboxed, opaque-origin iframe. The iframe's CSP disallows network access. No database secrets, app storage, DOM, or application API access are provided. Stop and hard deadlines terminate the iframe/worker; code never runs on the API server.
- A local Node API accesses real PostgreSQL through `pg`. PostgreSQL is installed on this machine, so local database bootstrap can satisfy persistence without a hosted account. Supabase is optional infrastructure for later use, not a claimed integration. PGlite and SQL exercise execution are deferred.
- Only the app server holds database connection details. Bind development services to loopback. This milestone remains single-user. The user authorized private hosted access from a school browser on 2026-10-07; hosted startup requires a strong password.

Early execution, isolation, cancellation, and persistence validation will be recorded in `docs/tasks.md` before the full UI flow is completed.

## Data and session lifecycle
Persist challenge definitions, versioned session challenge snapshots, drafts, notes, run results, assistance events, and submitted attempts in PostgreSQL. Persist the session start/deadline and pause state on the server so reloads do not reset time. Timed pause/resume extends the deadline by the actual pause duration; paused time is excluded from submitted elapsed duration. Restart creates a fresh session and keeps previous drafts/attempts. Autosave uses revisions to reject stale writes.

Submission captures the exact code and its matching run results, plus assistance used. Timed attempts are immutable and unique per session. After submission or expiry, practice can continue in a separate draft; each continuation submission is stored separately. Deadline enforcement belongs to the API as well as the UI. Expiry preserves the last server-acknowledged draft even if the browser is closed. Unexecuted timeout snapshots are labelled as such.

This is a personal practice tool: browser results are useful feedback, not trusted examination grades or a hostile-code multi-tenant service. Keep test harness state outside learner code, compare outputs outside the execution worker, limit outputs and run duration, and document residual browser resource limits.

## Running code
Run imports the editor module once in the isolated browser worker, without invoking any challenge tests. Add your own function calls and `console.log(...)` to explore behavior. Await async calls at the module top level. Run tests invokes every supplied test; logs identify the case that emitted them. Each execution has a 1.5-second hard deadline; compilation and sandbox startup each have a 5-second deadline. Stop cancels the active worker/sandbox. Console output is bounded (100 entries / about 24 KB per execution and 200 displayed entries per test run) and is cleared on session reload; it is not stored in PostgreSQL.

History defaults to successful submitted solutions, showing completion date/time and elapsed practice duration. All sessions remain available for inspecting failed, expired, and continuation attempts. The first successful submission in a session is retained as its completion record. Continuation duration adds active continuation time to the timed attempt duration, excluding the gap before continuation starts. Older attempt durations are inferred from the original timestamps.
